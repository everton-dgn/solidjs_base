## Catalogs and messages

`project.inlang/settings.json` defines `pt`, `en` and `es`, with English as the
base locale. Each page or component keeps `i18n/pt.json`, `i18n/en.json` and
`i18n/es.json` next to its code. Messages with two or more production consumers
can go to `src/i18n/`; the others stay in the consumer. The keys are global and
use the prefix of the owner, such as `home_title` and `themeToggle_select`.

```text
src/routes/(base)/(home)/
  index.tsx
  i18n/
    pt.json
    en.json
    es.json
```

Use the same set of keys and parameters in the three files. For example,
`"home_welcome": "Olá, {name}!"`, `"Hello, {name}!"` and `"¡Hola, {name}!"`. The
compiler generates functions and TypeScript declarations in `paraglide/`:

```tsx
import { m } from '@paraglide/messages.js'

export default function Home() {
  return <h1>{m.home_title()}</h1>
}
```

The functions check message names, the names and presence of the parameters and
the optional locale, for example `m.home_title({}, { locale: 'es' })`. The
`Locale` type comes from `@paraglide/runtime.js`. Simple interpolations accept
non-null values; validate domain data before translating it. Do not call
messages at the top of a module: SSR shares modules between requests. Use calls
in the component or getters in constants and in `route.info.seo`, as in the 404.

The lint applies `paraglide/no-dynamic-message-access` to the
`@paraglide/messages.js` alias and to the generated module
`@paraglide/messages/_index.js`. Use static references, such as
`m.home_title()`; `m[key]()` and copies of the namespace (`{ ...m }`) prevent
the analysis of the messages in use and are refused. To select a message by a
domain key, create an explicit map of functions, such as
`{ title: m.home_title }`, and call the chosen function inside the component or
getter.

Plurals use the Inlang message format, with declarations and selectors:

```json
{
  "cart_items": [{
    "declarations": ["input count", "local countPlural = count: plural"],
    "selectors": ["countPlural"],
    "match": {
      "countPlural=one": "{count} item",
      "countPlural=*": "{count} itens"
    }
  }]
}
```

Each locale can have its own variants, keeping the input parameters.

## Generation and validation

`@evertondgn/solid-tooling` finds the catalogs and generates the intermediate
aggregates in `.paraglide/messages/`. The official parser reads the messages,
and `checkBundle` from the Inlang SDK checks translations, variables and plural
forms in memory, without opening a database or running another CLI. The packaged
integration checks the folders, the locale names and the duplicates before
joining the files. A missing locale, key or parameter, an extra or duplicated
key, an empty message and invalid JSON stop the generation. No silent fallback
covers forgotten translations. The generated folders are ignored by Git; edit
only the colocated catalogs.

For a custom pipeline, `defineSolidApp({ i18nPlugin: false, ... })` disables the
automatic plugins. A replacement can be returned through `extend`; the
`i18n-generate` task can separately be replaced by name in `tasks`. The locale
providers and browser setup still follow the translation settings, so the custom
pipeline must produce their generated modules before they are used.

`vp run i18n:generate` prepares the aggregates and runs the official Paraglide
CLI through the package's compiled `i18n-generate` entry. `defineSolidApp`
enables i18n when `project.inlang/settings.json` exists, including in the `dom`
and `browser` Vitest projects. The application owns no generation script or i18n
plugin. In development and in the build, the packaged plugin prepares the same
aggregates and hands the compilation to the official `paraglideVitePlugin`. The
plugin keeps the cache, follows the files that the compiler uses and publishes
the updates through the Vite HMR. The packaged adapter handles the discovery and
validation of the colocated catalogs. Invalid catalogs or configurations block
responses in development; after the fix, the server serves again. A browser that
opened the text error page needs to reload it; clients already connected get the
overlay and the recovery through HMR.

The adapter groups the events of the catalogs, of `project.inlang/settings.json`
and of `project.inlang/paraglide.config.ts` before preparing the messages: it
waits 100 ms and restarts the wait when new relevant events arrive. The
sequential `watchChange` hook makes the official plugin wait for that
preparation before processing the same event. The `server.watch` options stay
under the control of the project; the i18n keeps the default, custom options and
`watch: null`. Code and CSS changes go on without that wait.

That window groups close events, without guaranteeing that a write has finished:
parts separated by more time can still expose an incomplete file. Generated
aggregates and modules do not trigger another preparation; identical content is
not written again. When the server closes, preparations and compilations already
started finish. Events that the watcher has not delivered yet are left for the
next start, which validates the catalogs again and updates the output. The type
check, `check:ci` and test scripts generate the messages before the validation,
in a fresh clone too. That standalone generation, the one of the pre-commit
`check:fix` included, runs in another process and does not join the queue of the
development server: a catalog saved between its read and the write of the
aggregates can have the newer aggregate, already prepared by the server,
replaced by the previous content. Since aggregates do not trigger a preparation,
the server keeps the old text until the next catalog event or the next start;
saving the catalog again solves it. The format plugin comes from the local
dependency, without downloading code from a CDN during the generation.

The cost of the generation grows with the whole set: each preparation reads and
validates again every catalog of every locale, and the Paraglide compiler loads
all of them at once. In development, this repeats on every saved catalog. None
of it runs on requests. The `CATALOGS_MAX_BYTES` limit, in
`packages/solid-tooling/src/i18n/readCatalogs/constants.ts`, limits the sum of
the catalog files: past it, the generation fails on the file that crossed the
limit, before reading it, instead of degrading the build. In measurements with
synthetic catalogs in three locales, 1 MiB (5,000 messages per locale) generated
in 1.2 s with 214 MiB of memory, 4.4 MiB (20,000) in 3.4 s with 650 MiB, and 8
MiB (36,000), the default limit, in 6 s with 1.1 GiB; the local preparation
takes about a tenth of that time, and the rest is the compiler. To go over the
limit, raise the constant after measuring the memory of the build environment.
The pipeline has no incremental mode: preparing only the changed catalogs would
require keeping the validated state of each folder between runs.

The compiler options are in `project.inlang/paraglide.config.ts`. The standalone
CLI and the development and build commands use Bun. The compiler itself reuses
the hashes of the output, writes the changes and removes stale modules from
`paraglide/`. Those generated files do not need the trash. The Vite+ task adds a
cache to the standalone command. The Markdown snapshots of the static pages come
from the prerender, after the compilation; in development, the middleware
converts the HTML on each request. None of these steps runs on the production
requests of the static pages.

The CLI and the plugin receive the options of
`project.inlang/paraglide.config.ts`, but, when the configuration does not
declare `isDevelopment`, Paraglide applies a different default on each path. The
CLI writes `true`. The plugin follows the `NODE_ENV` resolved by Vite
(`config.isProduction`), regardless of `--mode`: it writes `false` in the build,
in the E2E build with `--mode e2e` too, and `true` in the development server and
in Vitest. That is why `paraglide/runtime.js` and `paraglide/runtime.d.ts`
reflect the last write of `paraglide/`, and a cache hit of the `i18n-generate`
task counts as a CLI write: Vite Task restores the archived output, with `true`,
without compiling. When switching between the build and the other paths, the
next compilation (the build after the CLI, the development server or Vitest, or
the development server after a build) does not reuse the persistent cache of the
plugin, which checks the hashes of the output. No generated module and no
application code reads that constant; for your own diagnostics, use
`import.meta.env.DEV`. Declaring the value in the configuration makes both paths
the same, at a cost: a literal fixes the same value in development and in the
build, and a Vite expression gets the `any` type in `runtime.d.ts`.

The published plugin already includes the changes of
[upstream PR #820](https://github.com/opral/paraglide-js/pull/820): the Vite
`devErrorResponse` option, the wait for the pending compilation when the server
closes and the invalidation of the caches of that queue when it ends during the
shutdown. That forces the next start to compile again when a second write
arrives during the previous read and its event is dropped in the shutdown. The
dependency uses those implementations directly. The validation of the catalogs
stays in the adapter, with `checkBundle` from the official SDK. Paraglide keeps
`inlang check` as the only path for that check
([#794](https://github.com/opral/paraglide-js/pull/794)), and it reads only the
aggregates, without pointing to the colocated catalog that failed.

The bundler removes unused messages and keeps the messages exclusive to the page
in its lazy module. Each module holds the three locales of the messages it uses.
The experimental per-locale split is turned off to keep the streaming and the
CSP of the project. The i18n E2E test finds the lazy module of each page through
the exclusive message of the body in the three locales, checks that no other
module holds it, that the 404 downloads none of those modules and that the one
of the home page arrives on the navigation to it.

Custom `urlPatterns` require `URLPattern`. With `lazyUrlPatternPolyfill: true`,
the generated runtime only imports the polyfill when the native API is missing,
through an `import()` in a top-level await. Chrome and Edge for desktop and
Android, Firefox 142 or later and Safari 26 or later use the native
implementation and do not download that chunk; on the server, Node and Bun also
have the API and do not run the import. `vite.config.ts` does not set
`build.target`, so the build follows the default Vite Baseline, which still
accepts browsers without the API: Firefox before 142 and Safari before 26. On
iOS, every browser uses the system WebKit and depends on the same version 26.
Those browsers fetch the polyfill in an extra request before `entry-client`
runs, which delays the hydration on them. A failure of that request behaves like
the one of any initial chunk: the page stays with the SSR HTML, without
hydrating, and the outdated page detection never gets installed.
`I18n.urlPattern.production.e2e.test.ts` removes the native API in Chromium and
checks that only that path downloads the polyfill chunk, that the hydration ends
on both paths and that the links and the locale switch work without errors or
CSP violations.

## Negotiation and isolation on the server

Pages without a prefix get a temporary redirect, without cache, using the
`locale` cookie, then `Accept-Language` and finally `en`. The explicit URL takes
priority. The detection ignores locales with `q=0` and invalid weights; if no
accepted locale is available, it uses the base locale. The native Paraglide
parser does that detection without changing the original request. The middleware
isolates the locale of each SSR with `AsyncLocalStorage` and keeps
`Content-Language`, `<html lang>`, SEO and hydration consistent. Server
functions use the source page of the same domain, falling back to the cookie and
the language header, keeping the request body and the Solid control signals.
APIs, indexes and common assets stay without a prefix. The Markdown snapshots
are localized files, such as `/pt/about.md`, generated in the build with
isolation between the locales. The locale and the content of those files come
from the URL, regardless of cookies and `Accept-Language`; direct access does
not go through the localization of pages.

`packages/solid-runtime/src/middleware/requestClassification/` gathers the page
criteria used by the localization and by the failure containment. The
localization of GET and HEAD pages looks at the path, regardless of `Accept`, so
that pages excluded from the Markdown negotiation also render in the locale of
the URL. The failure containment keeps checking the accepted formats.
`persistLocale`, inside the localization middleware, serializes the server
cookie using the policy exported by the Paraglide runtime.

## Navigation

To navigate between pages, use `LocalizedLink`, `createLocalizedNavigate()` and
`localizedRedirect()`. All three keep the query and the fragment and accept the
typed paths of `paths`, which stay without a locale prefix; only the matching
removes that prefix. Relative paths are resolved against the current page in
links and in navigation. In redirects, the middleware provides the page URL in
the SSR; in HTTP calls of server functions, it uses the validated same-origin
`Referer`. Without a safe page base, the helper refuses relative targets. Paths
from the root work in that case too.

```tsx
import { LocalizedLink } from '@/components/atoms/LocalizedLink/index.tsx'
import { localizedRedirect } from '@evertondgn/solid-runtime/i18n/localized-redirect'
import { m } from '@paraglide/messages.js'
import { createLocalizedNavigate } from '@/primitives/createLocalizedNavigate/index.ts'
import { paths } from '@/router.ts'

// Inside a component under the Router:
const navigate = createLocalizedNavigate()
const home = <LocalizedLink href={paths}>{m.siteLinks_homeLabel()}</LocalizedLink>
const goHome = () => navigate({ href: paths, replace: true })

// In a handler, preload or server function, return or throw the Response:
throw localizedRedirect({ href: paths, status: 303 })
```

`locale` lets you choose another locale. `shouldLocalize: false` keeps endpoint
and file URLs without a prefix; in JSX, use `shouldLocalize={false}`. External
URLs, `mailto:` and `tel:` are kept too. Links keep native attributes such as
`target` and `download`. Navigation in the same locale uses the router; links
and programmatic navigation to another locale load the whole document. A guard
at the root of the router applies the same rule to the redirects of actions and
queries, and the guard of `entry-client/installLocaleHistoryGuard/`, installed
before the Router, covers the history between locales, to keep messages,
document and SEO in the same locale. `localizedRedirect()` keeps the status,
headers and control signals of the Solid `Response`. `state` and `scroll` only
apply to navigation through the router. Outside it, `LocalizedLink` accepts
paths from the root, but does not resolve relative paths. The low-level helper
`localizeHref()` is still available in `@evertondgn/solid-runtime/i18n/urls` to
build SEO and index URLs, such as alternates, the sitemap and `llms.txt`. It
hands the building of the URL to the native Paraglide `localizeHref` and keeps
the app rule of translating only paths from the root. The router turns on
`intentPreload()` explicitly to start the navigation early when interacting with
links, using the same `transformUrl` that removes the prefix in the matching.

Before the hydration, the client entry compares the locale of the current URL
with the one of the URL that loaded the document, recorded in
`PerformanceNavigationTiming`. If the history changed locale while the
JavaScript was loading, the entry reloads the selected URL before starting the
app. The query, the fragment and the state of the history entry are kept.
Changes in the same locale go on to the hydration without a reload. The `lang`
attribute does not decide that check: an error page can use the base locale
before there is a translation context. Without an available navigation entry,
the client goes on with the normal hydration.

Flows that need to warn about unsaved changes must also handle leaving the
document, as in the native `beforeunload` event. A `useBeforeLeave` guard on the
page, alone, does not cover the links or the programmatic navigation that reload
the document when switching locale.

## Preference and cookies

The switcher calls `setLocale()` and navigates the whole document to the chosen
locale. The native Paraglide `setLocale()` keeps the navigation and the
hydration when cookies are blocked; in that case the preference stays in the
URL. The guard in `entry-client/installLocaleHistoryGuard/` keeps the document
navigation in the history between locales. The server writes `locale` on page
responses and on negotiation redirects when the preference does not match the
resolved locale yet. Those responses use `private, no-store`; `Vary: Cookie` is
added without erasing the existing values. The cookie uses `Path=/`,
`SameSite=Lax`, `Secure` on HTTPS and the duration set by Paraglide.
`cookieSameSite: 'lax'` and `cookieSecure: 'auto'` are in
`project.inlang/paraglide.config.ts`, with the same policy on the client and on
the server. Server function calls do not overwrite the preference of the page.
The client also updates the cookie during the hydration and in the locale
switcher.

## SEO indexes

The sitemap publishes one URL per locale, with reciprocal alternates and
`x-default`. The count and byte limits are checked after that expansion.
`llms.txt` uses English and `/en` URLs to keep a single, cacheable index.

## Runtime request step

The chain creates `createLocalizeRequest({ applySecurityHeaders })` from
`@evertondgn/solid-runtime/middleware/localize-request`. Markdown response
helpers use the same factory and security header instance. Locale detection,
cookie persistence and the safe page base belong to the runtime. The application
keeps its catalogs, compiler settings, navigation components and middleware
chain.
